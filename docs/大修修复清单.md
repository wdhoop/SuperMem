## 二、P0 三条

### P0-1 权重下限封死归档

**现象**：`compute_weight` 对每天衰减叠加 `FLOOR_BY_TYPE` 下限，A/B/C 类节点下限分别是 0.5/0.3/0.2，衰减到下限后再也不动；`archive_nodes` 用 `weight < 阈值` 判定归档，结果**一条都不会被归档**，老记忆永久占位。

**修法**（`config.py` + `core.py`）：
- `FLOOR_BY_TYPE` 重设为 S 0.8 / A 0.35 / B 0.15 / C 0.05，让 C 类（闲聊、流水）真的能掉到底。
- `compute_weight` 的 age 基准从"写入时间"改为"最后活跃时间（last_accessed / timestamp 取大）"——不再惩罚"老但一直在用"的记忆。
- `apply_decay` 跳过 `obsolete` / `merged` 状态，避免对已归档节点重复计数。
- `archive_nodes` 真正执行归档：置 `obsolete`、写 JSONL 归档文件、**保持状态不被后续 decay 覆盖**；不再新增 `archived` 状态（沿用既有 `obsolete`，避免状态机膨胀）。
- 新增 `indexable_node_count`，`/rebuild`、`verify_index` 只统计可索引节点（排除 merged）。

**验证**：`verify_floor.py`、`diag_decay.py`、`verify_archive_chain.py`（在 178 套件里 6/6 通过），归档样本 `event_20261113_254e7b39` 已确认 obsolete + JSONL 落地。

### P0-2 锚点固定加成 + 关联扩散污染排序

**现象（两层）**：

1. **锚点固定加成**：命中实体钩子的节点直接 `+0.03`。而 RRF 基准分是 `1/(60+1)=0.0164`，等于 **+83%** 的固定加成——一条只靠钩子命中的节点能把正常结果全顶下去。实测挤掉 10 条本该第一的正确答案。
2. **关联扩散净拖累**：`related` 边扩散把邻居并进 RRF，权重与向量第 1 名同权，每查询平均灌 12.8 个候选。质量对照显示：**关掉扩散 @1 = 53.0%，开着 @1 = 34.3%**，即扩散抢走了 22 个百分点的 top1。

**修法**：
- 锚点改"乘性 + 小额绝对底"：`base = rrf*(1+0.35*strength) + 0.004*strength`。锚定只放大节点已有的排序地位，纯钩子命中最多进候选池、进不了前排（`ANCHOR_BOOST_REL` / `ANCHOR_BOOST_ABS`）。
- 扩散加三道闸：只扩散 `strength ≥ 0.55` 的边、上限 8 个邻居、权重下调。
- 扩散分**单独记账**（`related_rrf`），不再并进主 RRF：主路候选（向量/关键词/锚点/因果等命中）的分数完全不受扩散影响；只有"主路一条没召回到"的邻居才用扩散分兜底（只补位）。
- 同一候选的扩散分**只计一次**，不再按命中次数累加（原实现被 20 个种子反复命中后能叠到 0.02+，正好越过向量第 1 名 0.0164）。
- 最终排序加分段：主路命中优先，仅扩散召回的候选统一排后（`_final_order_key`，recall 与 rerank 共用）。

**验证**：4 组对照（A 现状 / B 关锚点 / C 关扩散 / D 全关）复测；现在 **A 与 C 完全一致**（74.6/94.0/99.3，MRR 0.846），即扩散已不再拖累，扩散只在前 20 名以外补位。

### P0-3 中文长句不切词

**现象**：中文查询整串当一个大 gram 去 `instr` 匹配，长句几乎必然落空；短查询又会命中半库。

**修法**（`search_fusion.py`）：
- `_tokenize` 重写：中文按 2-4 字滑窗切 gram，英数按词切，过滤停用虚词，长句保底保留长 gram。
- `_fts_recall` 从"拉全表到 Python"改"SQL 先筛命中行再算分"（1 万节点 115ms→24ms）。
- 加命中门槛：至少命中一个 ≥2 字 gram，且"命中 ≥2 个 token 或命中最长 gram ≥4 字"——否则"记忆""系统"这种高频二字词会让半库节点拿 0.6 分。
- 长 gram 命中分封顶 0.85，避免碎词拼凑的假高分。

## 三、P1 / P2 逐条

### P1-4 边类型被压平成 related
`normalize_edge_type` 先查白名单，未命中一律落 `related`。而白名单里**没有 `trigger` / `enable`**，导致 `/extract`、`/sync/apply` 提交的因果边全变 related（全库 related 占 97.6%）。
修：`EDGE_TYPES` 补 `trigger` / `enable`，`CAUSAL_EDGE_TYPES` 同步补 `trigger`，`event_normalizer` 的 alias 表补 trigger / related 族。迁移脚本把存量 `relate` / `RELATES_TO` 统一成 `related`（13 条 `resolve` 不映射，保持原样）。

### P1-5 grade 只算一次
`compute_grade` 只在 `add_node` 时算一次，之后无论 `access_count`、`confidence`、`status` 怎么变都不重算，经验卡永远停在初始档。
修：`touch` 在锁外重算 grade；**并且** `update_node` 一处兜住所有状态变更入口（见 #24）。
配套脚本：`audit_grade.py`（只读审计）、`refresh_grade.py`（`--apply` 幂等纠偏）。

### P1-6 gap 口径错
`/health`、`/stats` 的 `vector gap` 用"节点总数 - 向量条数"算，把 merged / obsolete 也算进缺口，永远不为 0。
修：两端统一按 `indexable_node_count` 口径算，实测 gap = 0。

### P1-7 causal_density 必崩
函数内引用了未定义的局部变量，任何调用都抛 NameError。
修：补齐取数逻辑（按 from_id 统计、边类型过滤）。

### P1-8 中断预算读一次扣一次
`interrupt_budget` 把"读剩余额度"也当成一次消耗。
修：`exhausted` 改纯查询、`spend` 是唯一递增入口、`__exit__` 置 `closed`、新增 `used` 只读属性。

### P1-9 cycle_detector 不区分边类型
`detect_all_cycles` 把 `related` 这类无边语义当成因果环，反复报假环；且递归实现在深链上会爆栈。
修：迭代版 Tarjan SCC + 只对 `CAUSAL_EDGE_TYPES` 建图。（注：`would_create_cycle` / `detect_all_cycles` / `causal_density` 在生产代码中暂无调用方，本轮修的是"能被正确调用"。）

### P1-10 非法输入返 500 且已写入
`_read_body` 遇坏 JSON 直接抛异常，且部分入口在参数校验前已经把半条数据写进库。
修：`_read_body` 坏 JSON → 400；`ValueError` 统一映射 400；`/extract` 先校验再落库；404 统一处理。

### P1-11 标签双转义
写入时对 tags 再做一次 JSON 编码，库里出现 `[\"a\",\"b\"]` 这种字面串，检索和展示都错。
修：`_load_tags` 幂等解两层、`add_node` / `update_node` 归一；迁移脚本修存量。

### P1-12 /mark 改状态不删向量
节点被标成 obsolete 后向量还在，检索仍能召回已废止内容。
修：`/mark` 同步删向量；`node_lifecycle.merge_into`、`selfcheck` 的 7a 步骤同步补删。

### P2-1 ~ P2-10
- **P2-1** `/episodes` 默认 50 条且不支持 limit → 加 `limit` 参数 + 返回 `count`。
- **P2-2** `/episodes` 查不存在 id 返 200 空数组 → 返 404。
- **P2-3** `recency` / `goal` 传非法值抛 500 → 归一到 400。
- **P2-4** `/timeline` 只传纯日期返空 → 支持路径式写法 + `end_of_day` 补齐时段边界。
- **P2-5** selfcheck 只报告不修 → `duplicate_edges` 真删、重复边去重、向量补齐。
- **P2-6** 时间戳 4 种格式互不兼容（`2026-11-13`、`2026-11-13 10:00:00`、ISO、带 T）→ `_parse_dt_any` 五格式统一；写入侧统一带秒；迁移统一存量。
- **P2-7** 同一语义三种写法（`relate` / `RELATES_TO` / `related`）→ 统一小写 + 单一别名表。
- **P2-8** 4 组重复边 → `add_edge` 去重全进锁；迁移清存量；新增 `duplicate_edges` / `dedup_edges`。
- **P2-9** MCP 错误被包进 result 让客户端拿不到 → `McpError` + `-32601` / `-32602` + 顶层 `error` 字段。

### P2-11 session 字段覆盖不全
复核结论：**不是可修缺陷**。`nodes` 表没有 `session` 列，会话归属本来就靠 `project` + `tags` 表达（如 `tags=["session:xxx"]`）。原报告的判断基于"应该有 session 列"的假设，与库结构不符。处理方式：不新增列（会破坏既有查询与迁移），在该报告第四节如实说明。

## 四、本轮新暴露的 3 条

### #24 状态变更不同步 grade（P1）

**怎么发现的**：写完 P1-5 的 `refresh_grade` 后，用 `audit_grade.py` 重算全库 grade 与库内值比对，发现 6 条不一致：2 条 `merged` 仍是 experience（应为 hint），4 条 `permanent` 仍是 hint（应为 experience）。

**根因**：`set_status` / `mark_permanent` / `mark_outdated` / `merge_into` / `archive_nodes` 都只 `update_node(node, {"status": ...})`，不重算 grade。P1-5 只修了 `touch`，漏了状态入口。

**修法**：在 `core.update_node` 一处兜住——锁内、构造 `fields` 之前判断 `if "status" in fields and "grade" not in fields: node.grade = compute_grade(node)`，一处覆盖上述 5 个入口。

**验证**：`refresh_grade.py --apply` 纠偏 6 条（2 条 experience→hint，4 条 hint→experience）；纠偏后审计 2289 条 0 不一致。本轮全部套件跑完、库增长到 2315 条后再审计，仍 **0 不一致**（experience 571 / hint 1744）。

### #25 FTS 候选窗口丢老节点（P0）

**怎么发现的**：把扩散改成"只补位"后，A 组 @1 与"关扩散"的 C 组完全一致（53.0%），但 C 组本身比修复前基线 65.4% 低 12 个点——说明还有一处独立回退。

**根因**：`_fts_recall` 为控内存，SQL 加了 `LIMIT max(64, top_k*8) = 320`，且 `ORDER BY timestamp DESC`。**这两条一起等于"只保留最新的 320 条命中行"**——正确答案常是老节点，被整批丢掉。中文长句切词后命中行上千，这个截断几乎必触顶。

**修法**：窗口提到 2000（主库 2289 条规模内不会误伤）。实测窗口 800 时 @1 反而掉到 72.4%，且 p95 延迟无变化（415→422ms），说明 p95 高不是这个窗口造成，质量优先取 2000。

**效果**：C 组 @1 53.0% → **74.6%**，@3 74.6% → **94.0%**，@10 93.3% → **99.3%**，未召回 9 → **1**。

### #26 关联扩散按命中次数累加（P0）

**根因**：`if rec["related"] == 1` 之前没有这层判断，同一邻居被 vec top10 + fts top10 反复命中就反复加分，热门邻居 RRF 叠到 0.02+，越过向量第 1 名的 0.0164。

**修法**：每个候选只计一次扩散分量（配合 #P0-2 的"单独记账"）。

**效果**：这是"关扩散反而更准"的直接机制解释之一。
