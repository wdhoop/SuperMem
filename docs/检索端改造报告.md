## 一、五条结论先看

1. **三条改造全部跑通，全量、非最小版。** 拒答、经验转正、锚定钩子都在测试库上端到端验证过，代码仍在 lab，没有碰生产。
2. **拒答判据 10/10 判断正确**：6 个库内问题没有一个被误判成"没有"，4 个库外问题（汤团猫 / 嘉兴天气 / 红烧肉 / 量子退相干）全部 `no_match`，锚定命中 0。
3. **锚定钩子把三处关键排序拉回正位**：`125B 推理速度慢` 从"数据库查询太慢"换成"125B 速度基线"；`小妖 3D 形象重构` 换成"小妖已接入抖音完全体技能"；`Strata 是什么` 换成"待验证 Strata max_tokens=12000"。另外 `SuperMem 记忆检索` 从误拒（no_match）修回 hint。
4. **锚定层的成本几乎为零**：7097 节点库上，现有 `_fts_recall` 全表扫 **80.3ms**，锚定查表 **0.356ms**——快 225 倍。整条检索端到端 37–60ms（不含首次加载模型 6 秒）。
5. **最刺眼的问题不在检索算法，在"证据类型漏了两块"。** 查清后的真实分布是：生产副本 2144 节点里 event 占 1157（54%，不是 98%——那个数是 bench 库的），另有 insight 174、fact 50、experiment 20、milestone 15。原来的证据类型配置只认 decision/rule/technique/project/goal，把后面这四类**整类挡在门外**，而其中 119 条 insight 已经满足"置信度≥0.8 且被访问≥2 次"，内容全是"结论：LoCoMo F1=0.4308""坑：surface 配置在 %APPDATA%""根因：pull 水位游标未重置"。补齐后转正数 336 → 516。

   同时，event 不能发经验牌（那是流水账冒充结论），但"永远只能说线索"也不对——因为回答 125B 那个问题的最佳命中就是一条事件记录。所以新增了第四档 `record`：可以答，但明确标"这是一条记录，不是结论"。

## 二、三条改造分别做了什么

| 改造 | 一句话 | 回落位置 |
|---|---|---|
| ① 检索端拒答 | 库里没有就直说没有，不再硬凑答案 | `search_fusion.judge_verdict()` |
| ② 经验转正标记 | 节点带 `grade`：`experience` 可作依据，`hint` 只能当线索 | `core.compute_grade()` + `nodes.grade` 字段 |
| ③ anchor 钩子层 | 写入时建"词 → 节点"路由表，检索时零成本查表 | 新模块 `anchors.py` + `anchors` 表 |

**拒答判据顺序**（任一条件成立即收口）：

1. 没有结果 → `no_match / no_results`
2. top1 分数低于绝对地板 0.02 → `no_match / below_floor`
3. top5 里既无锚定命中、也无字面命中 → `no_match / no_lexical_or_anchor_support`
4. **top1 本身是转正经验** → 继续走第 6 步
5. **top1 是一手记录**（event/state/todo/task）→ 排序明确给 `record / record_only`，排序挤在一起给 `hint / margin_flat`
6. top1 是其它未转正内容 → `hint / top1_not_evidence`
7. top1/top2 分数比 < 1.25 → `hint / margin_flat`；否则 → `answer / ok`

第 4–6 步是这一轮新加的。之前是"top3 里出现过 experience 就给 answer"，实测出现自相矛盾：`125B` 的 top1 是一条事件流水（hint 级），系统却对外说"这是答案"。改完又发现"不是经验就一律 hint"会把唯一能答的那条打死，于是补了 `record` 这一档。

**四档含义**：

| verdict | 含义 | 调用方该怎么用 |
|---|---|---|
| `answer` | 最佳命中是转正经验，排序明确 | 可以直接当初结论引用 |
| `record` | 最佳命中是一手记录，排序明确 | 可以答，但要声明"这是记录，不是结论" |
| `hint` | 只能当线索 | 作为提示，不能当答案 |
| `no_match` | 库里没有 | 直说没有 |

## 十二、钩子表容量与淘汰行为实测（2026-11-12 补测）

**一句话结论：表不会爆（20000 行硬上限确实生效），查表也不慢（毫秒级且与规模无关）；但表满后最先被删的是最有价值的实体锚点，这是个真缺陷，得修。**

### 查表耗时（临时副本实测，3 个真实 query 平均取中位）

| 表行数 | 词数 | hook_recall |
|---|---|---|
| 6,653 | 1,431 | 0.233 ms |
| 10,000 | 3,105 | 0.175 ms |
| 20,000 | 8,105 | 0.173 ms |
| 20,000（超限回收后） | — | 0.359 ms |

查询走 `term` 索引 + `IN (n-gram)`，成本只取决于命中的行数，**不随表变大而变慢**。对比 `_fts_recall` 全表扫的 80.3 ms，钩子路仍是快 200 倍以上。

### 写入与回收成本

- 单次 `index_node`（写 3 个词，表 20000 行）：**4.8 ms**
- 表超上限时 `_enforce_ceil` 回收（50000 → 20000 行）：**113 ms**（只在这批次写入时阻塞一次）

### 增长速率

放进一条新记忆 = 最多 +12 行（`ANCHOR_MAX_TERMS_PER_NODE`）。当前 6,653 行，距 20000 上限约 **1,112 条新记忆**。按每天 20 条算约 55 天填满。

关键：全量重建（`build_index`）卡了 `ANCHOR_MIN_DF=2` 闸门会砍掉私有词，但**增量写入不卡闸门**，所以单条新记忆能塞 12 行 df=1 的私有词进去。

### 缺陷：淘汰顺序把最该保的先删了

生产实况：`anchors` 表 **hits 全部为 0**（6653/6653 行），因为 `hook_recall` 检索命中时从不累加 hits。

而 `_enforce_ceil` 的淘汰排序是：

```
ORDER BY hits ASC, updated_at ASC LIMIT (total - MAX)
```

hits 恒为 0 → 退化成**纯按时间淘汰，最老的行先删**。迁移时建的 6,653 行（含 Strata/Hive/SuperMem 这些实体锚点）正是最老的，新记忆写入时逐条被删。

模拟实测（从 6653 行起，每条新记忆写 12 个新词）：

| 写入条数 | 表行数 | Strata | Hive | 小妖 | SuperMem |
|---|---|---|---|---|---|
| 1 – 1100 | 6,665 – 19,853 | 100 | 79 | 38 | 58 |
| **1,113（首次触顶）** | 20,000 | 99 | 78 | 38 | 57 |
| 1,200 | 20,000 | 68 | 46 | 38 | 40 |
| 1,300 | 20,000 | **36** | **36** | 29 | 35 |

**第 1113 条新记忆开始，实体锚点就被逐条挤掉。** 再往后表大小恒定在 20000，但内容持续被新词替换 —— 不是爆炸，是慢性失血。按这个速率，3–4 个月后 Strata/Hive 这类核心实体锚点会被冲掉一半以上，改造在检索端等于失效。

### 万节点压测暴露的两个问题：复核结论

**问题 1（原判「中文词 df 上限 50 偏紧」）—— 复核后不成立，不改。**

原判断依据的是构造数据：我把 anchors 表人为推到 20050 行时反复复用同几个词，导致「用户」df 涨到 435。那是构造方式的产物，不是真实增长。

直接查两个真实库的词频分布：

| 库 | 节点 | 中文词数 | 中文词最高 df | df≥50 的中文词 |
|---|---|---|---|---|
| 生产库 | 2148 | 276 | 小妖 38 | **0 个** |
| 万节点压测库 | 10300 | 3234 | 用户 32 | **0 个** |

生产中文词 top10 是 小妖 38 / 天网 26 / 方案 23 / 决策 19 / 庙小妖 19 / GPU解锁 17；万节点库中文词 top10 是 用户 32 / 小满 12 / 我什么都没干 12 / 十种食物不能一起吃 10 / 辛苦了 10。

结论：**中文词 df 离 50 还有距离，1 万节点也没越线**，而且 3234 个中文词里 96% 是 df=1 的私有词（真实记忆的典型形态）。放宽上限在当前和万节点规模上都不会带来任何收益，只会让泛词更难被清掉。**保持 50 不动。**

**问题 2（`_fts_recall` 与节点数近线性）—— 确认属实，已修，见第五步。**

**第五步：关键词路从「全表拉成对象再逐条比对」改成「SQL 层先筛」（2026-11-13 第五次上线）**

`_fts_recall` 原实现是：

```python
nodes = ms.graph.list_nodes(project=project, limit=100000)   # 每行都转成 Node 对象
for node in nodes:                                            # Python 里逐条
    cl = (node.content or "").lower()
    if ql in cl or ql in tl: ...
```

也就是说：**它不是索引查询，而是把一万行全部实例化成 Python 对象，再逐条做子串匹配**。节点一多，对象构造 + 循环次数同步增长，这就是 +41% 节点 → +43% 耗时的原因。

改法：把粗筛下推到 SQLite（C 层扫描字符串，不构造对象），只把真正命中的行转成 Node，再在命中集里算原来的分数：

```python
sql = "SELECT * FROM nodes WHERE status != 'obsolete'"
sql += " AND (" + " OR ".join("(instr(lower(content),?)>0 OR instr(lower(tags),?)>0)" for t in toks) + ")"
rows = ms.graph.conn.execute(sql, args).fetchall()   # 只回命中行
```

打分规则、排序、top_k、max_turn 过滤全部原样保留。

**正确性验证**（两库 × 10 条 query，逐条比对结果集 id 顺序和每一项分数）：

| 库 | 旧合计 | 新合计 | 加速 | 结果一致 |
|---|---|---|---|---|
| 生产库副本（2147 节点） | 235 ms | 51 ms | 4.6× | 10/10 一致 |
| 万节点库副本（10300 节点） | 1135 ms | 242 ms | 4.7× | 10/10 一致 |

单条最快 9.0×（"小满今天说了什么" 26.4→2.9 ms），最慢 2.8×（"小妖 3D 形象" 23.3→8.3 ms，因为命中的行多、后续算分成本占主导）。

**判据快照对比**（lab 库，13 条 query 改前/改后各跑一次，比 `verdict`、`verdict_reason`、`top1_id`、`top1_score`、`fts_sim`、前 5 结果 id）：**差异 0 条**。

**生产上线**：备份 `search_fusion.py.bak_pre_ftsswap_20261113`（34100 字节）→ 覆盖（34827 字节）→ `py_compile` 通过 → 重启。PID 276564 → **66276**。冒烟：`/health` ok，nodes 2148、edges 26444、episodes 98、vector_indexed 2147（gap 1）；`125B=record/record_only`、`Strata=hint/margin_flat`、`嘉兴天气=no_match`，与改前逐条一致。13 条 query × 3 次 HTTP 实测中位 **165 ms**（94–264 ms）。

### 还没做的

- **关键词路仍是全表扫，只是从 Python 移到了 SQLite C 层**。`instr` 用不到索引，所以耗时长仍随节点数线性增长，只是系数小了 4.7 倍。10 万节点时大约 240 ms，虽不再是秒级，但仍是扩容时第一个要动的地方，真正的解法是 FTS5 或自建倒排索引（未验证成本）。
- **并发瓶颈不在钩子层**。HTTP 并发压测（lab，18888）：串行 P50 152ms、4 线程 867ms、8 线程 2445ms，而钩子层写回成本只有 0.3–21ms。真实主因是每次检索 ~150ms 的 embedding（CPU 推理）+ 单 SQLite 连接全局锁串行。改并发架构（连接池/多进程/GPU 推理）超出本轮范围，且生产实际并发低。
- 生产上没跑 A/B（怕打扰正在用库的智能体）；判据行为按 lab + 生产抽样对齐。
- 万节点压测跑在隔离的 `smem-scale`（7078→10000），生产库仍是 2147 节点，**没有在万节点生产规模上做真实 A/B**。
- `_prune` 只在万节点副本上量过耗时（61.5 ms），生产从上线起没跑过全量重建，真实触发时什么表现仍是未知。
- 表满回收已改“一次多删留缓冲”（删到 19000），生产已上线；但 1000 行缓冲是按每天约 20 条新记忆估的，写入速率若突然放大要重估。
- `status=confirmed` 机制空转：库内 `confirmed` 为 0，`GRADE_CERTAIN_STATUSES={confirmed,permanent}` 永不触发。补签发流程成本高且无人使用，本轮不动。
- grade 是否按 node_type 分档（event 靠 status+边支撑+新鲜度，decision/rule 靠 confidence+access）仍待定。
