# 权重与衰减机制失效：从现象到断根修复（2026-11-07）

> 一句话结论：旧记忆之所以"越错越牢"，不是因为衰减档位没设计，而是因为**时间戳解析失败让 76.5% 的记忆永不折旧**，同时**访问次数被乘进权重**，让被反复检索的错误条目长期顶格 1.00。两处叠加后，"新记忆权重更高"这个假设在代码里根本不成立。

## 一、现象

一次关于本地模型量化档的问答里，检索命中了 2026-10-10 的旧结论（"Q2_0 崩坏、已弃用"），而当天稍早刚写入的正确结论排在后面。旧条目被答错后又被检索命中一次，访问次数 +1，权重更满，下次更优先——形成"越错越牢"的正反馈。

## 二、根因

### 1. 时间解析失败 → 76.5% 的节点永不衰减

`_age_days()` / `_access_age_days()` 只认 `"%Y-%m-%d %H:%M:%S"` 一种格式，失败后静默兜底为"现在"（`created = now`，age = 0）。而真实库里的时间戳大量是：

- `2026-09-30 17:23`（缺秒）
- `2026-05-05T09:14:00+08:00`（ISO 带时区）
- `2026-05-13`（纯日期）

age = 0 → `e^(-λ·0) = 1` → 衰减项恒等于 1，这条记忆永远不会折旧。

生产库实测：**1953 个节点中 1494 个（76.5%）** 的时间戳按旧格式无法解析。

### 2. 访问热度乘进权重 → 权重被访问次数顶格

旧公式：

```
heat = access_count × e^(-0.02 × 距上次访问天数)
causal_factor = min(1 + 0.3 × edge_count × heat, 2.0)
W = 0.7 × e^(-λt) × causal_factor × status_mod
```

只要 `access_count ≥ 6`，`causal_factor` 就被截到上限 2.0，`0.7 × 2.0 = 1.4`，再被 `min(1.0, …)` 截到 1.00。实测 **1030 个 active 节点权重 ≥ 0.99**。

而新写入的条目 `access_count = 0`、`heat = 0`、`causal_factor = 1.0`，出生权重 `W0 = 0.7`——**从出生那天起就比老条目低 0.3**，永远排不到前面。

### 3. 档位衰减存在但 A 档偏软

| 档 | 类型 | λ | 半衰期 | 下限 |
|---|---|---|---|---|
| S | permanent / 长期 | 0.0005 | ≈ 6.9 年 | 0.80 |
| A | decision / project | 0.0030 | ≈ 231 天 | 0.35 |
| B | task | 0.0080 | ≈ 87 天 | 0.30 |
| C | insight / 其它 | 0.0300 | ≈ 23 天 | 0.20 |

关键结论绝大多数是 `decision` → A 档，半衰期 231 天，等于"决策类几乎不衰减"；再叠 `causal_factor = 2.0` 顶格，退化路径就是"衰减看不见"。

### 4. 检索精排层没有 recency

- `RECALL_WEIGHTS = {vector 0.35, tag 0.20, recency 0.20, weight 0.15, access 0.10}`
- `RERANK_WEIGHTS = {vector 0.50, weight 0.25, edge_count 0.15, access 0.10}`

精排里 `recency` 完全缺席，而 `weight`（顶格）与 `edge_count`（老条目边多）都在，新旧对撞时新条目必输。

### 5. 自动退休只认关键词

`linker.py` 的 `auto_supersede_link` 要求新内容命中 `SUPERSEDE_KEYWORDS`（放弃/不再/改为/推翻/作废…）且与旧节点相似度 ≥ 0.50，才把旧节点转 outdated。配置变更类记录若不含这些词，旧结论不会被退休——"库不知道配置变了"。

## 三、修复

改动集中在 `core.py` 与 `config.py`，不动检索链路与评测口径。

### core.py

1. 新增 `_TS_FORMATS` 与 `_parse_ts(value)`：优先 `datetime.fromisoformat`（去时区），失败逐个 `strptime` 回退（含缺秒、纯日期、斜杠日期、微秒）；**全部失败返回 None，不再伪造 now**。
2. `_age_days` 改用 `_parse_ts`，`created_at` 解析失败时回退读 `node.timestamp`。
3. `_access_age_days` 同样改用 `_parse_ts`。
4. `compute_weight`：
   - 去掉 heat 乘子，`causal_factor = min(1 + 0.3 × log1p(edge_count), CAUSAL_FACTOR_MAX)`——边数用对数压缩，避免边多即权威；
   - 乘 `newness`：写入 7 天内 ×1.2，让新结论先压过旧的；
   - 访问量不再参与权重，只保留在检索排序的 `access` 分量（排序用，不定性）。

### config.py

```python
CAUSAL_FACTOR_MAX = 1.3   # 原 2.0；0.7*1.3=0.91 < 1.0，不再全民顶格
NEWNESS_BOOST = 1.2
NEWNESS_BOOST_DAYS = 7
```

`ACCESS_HEAT_LAMBDA` 保留（检索侧/历史兼容），但 `compute_weight` 已不再引用。

新公式：

```
W = min(1.0, max(floor, W0 × e^(-λ·age) × (1 + 0.3·log1p(edges)) × status_mod × newness))
```

## 六、已知未修（有意保留）

- **精排层仍无 recency**：`RERANK_WEIGHTS` 保持原样。理由：改动会连带影响已有评测基线（LoCoMo / LoCoMo-Plus）的可比性。本次修复已把 weight 恢复为有区分度的信号，精排的 recency 可作为独立一轮改动评估后再上。
- **自动退休仍只认关键词**：`auto_supersede_link` 的触发条件未放宽到"同 tags + 同实体自动退休"。放宽的收益是配置变更类记录无需特定措辞即可退休旧条，代价是同主题下多条并行结论可能被误杀，需先设计白名单/人工确认机制。

## 七、教训

1. **静默兜底是隐形 bug 源**：`except: created = now` 这种"让它别崩"的写法，把 76.5% 的记忆变成了永不折旧，且没有任何日志。解析失败应当显式表达（返回 None）而不是伪造一个合理的值。
2. **不要把"使用频率"混进"可信度"**：访问次数反映的是"被检索到"，不是"被验证过"。错误记忆被检索命中本身就会拉高访问次数，把访问量乘进权重等于给错误记忆自我强化。
3. **顶格封顶要留出余量**：`W0 × 上限 > 1.0` 的设计（0.7 × 2.0 = 1.4）会让任何有边的老条目都撞到天花板，权重信号直接失效。上限应当保证乘出来小于 1.0。
